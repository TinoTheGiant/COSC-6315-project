\section{Introduction}

A distributed database splits its data into pieces and spreads those pieces
across machines in different places. The pieces are called shards. Two
decisions matter. The first is where the boundaries between shards fall. The
second is which machine holds each shard. Both are normally made once, when
the database is designed, and the placement is then decided by a function of
the key, such as a hash. A hash does not know where requests come from.

That is fine whilst the traffic stays where the designer expected. It is not
fine in a service with users on several continents, served by a database
spread across regions in the manner of Spanner~\cite{corbett2013spanner} or
CockroachDB~\cite{taft2020cockroachdb}. The geographic centre of the traffic
moves across the day as one region wakes and another sleeps, so a placement
chosen for the morning is wrong by the evening. Every request that crosses an
ocean to reach its data pays that ocean's round-trip time, and a transaction
touching shards in several regions pays it more than once, because keeping
such a transaction atomic needs more than one round of agreement between the
machines holding those shards.

The obvious response is to move the data when the traffic moves. A simple
rule does this: every decision window, find the shard whose placement is
costing the most and move it towards the region reading it. I implement that
rule as a baseline and call it \emph{follow traffic}.

This paper asks whether a policy learned from experience does better than
that rule. The answer turns out to depend on how fast the traffic moves. When
the drift is slow, the simple rule is within half a millisecond of the best
placement that moving shards can reach, so there is nothing worth learning.
When the drift is fast, the same rule falls 57\,ms short of that reference,
which is 41\% of its own latency, because it always reacts one window behind a
target that has already moved again. The room for a learned policy is largest
exactly where the problem is hardest.

The paper builds a simulator of a six-region cluster whose traffic drifts on
a daily cycle and spikes locally, states placement on it as a reinforcement
learning problem with 261 possible actions, and measures four reference
points against it: fixed hash placement, random movement, the follow traffic
rule, and a cost-free reference showing what good placement is worth when
movement is not charged for. It checks on a real six-node CockroachDB cluster
that placement changes measured latency by far more than the measurement
noise. It then trains a Deep Q-Network at the fastest drift setting, where it
beats both the rule and fixed placement on the combined cost.
