\subsection{The simulator}

The simulated cluster has six regions, one node in each, and three copies of
every shard. The keyspace is divided into 256 cells, and shards are built from
runs of those cells. An episode is 200 decision windows and the simulated day
is 96 windows, so one episode covers about two days.

Traffic comes from a centre of demand that rotates around the regions on that
daily cycle, with local spikes on top. A single number, \emph{volatility},
scales how fast the centre rotates and how often and how hard it spikes, so
one setting moves the environment from placid to violent. It is the main thing
the experiments vary.

\subsection{What the agent sees and does}

At each decision window the agent is shown the read and write counts for each
region from the window just finished, where every shard currently sits, how
big each shard is, how much data has moved recently, and the matrix of
round-trip times between regions.

It then picks one action from 261. There are four kinds. \textsc{move\_lease}
makes a region the primary copy for a shard, which moves no data and is only
legal where that region already holds a copy. \textsc{move\_replica\_to} puts
a copy of a shard in a region, dropping the existing copy furthest away so the
number of copies stays the same, and this one does move data.
\textsc{split} divides a shard at its midpoint. \textsc{noop} does nothing.

Every action names a desired end state rather than an operation, so every
action is defined in every state, and one that cannot be applied resolves to a
small penalty instead of an error. This matters because the kind of network
used here cannot be told which actions are illegal.

\subsection{What the agent is scored on}

The agent minimises one combined cost,
%
\begin{equation}
c = \frac{\ell}{100} \;+\; w \cdot \frac{g}{2000} \;+\; 0.10 \cdot b
\label{eq:objective}
\end{equation}
%
where $\ell$ is mean transaction latency in milliseconds, $g$ is gigabytes
moved over the episode, $b$ is load imbalance, and $w$ sets how much movement
is charged for. In plain terms: latency is the thing to make small, moving
data is charged for, and piling the whole workload onto one node is charged
for separately, so a policy cannot win on latency by overloading one region.

Movement is charged as a fraction of the dataset rather than in bytes. This is
deliberate. A 60\,GB simulator and a 1\,GB cluster then score the same
physical move identically, so a policy trained in one can be scored in the
other without the reward changing meaning underneath it.
